# ADR-011: The Project takes requests to an issue; the loop builds it

- Status: Accepted (changes part of ADR-010)
- Date: 2026-10-26

## Context

ADR-010 had cloud threads of the Claude Code Project create the issue, implement it and open the pull request. The first task done that way (issue #31, PR #32) showed three gaps. Every GitHub write from the cloud gets a "Generated by Claude Code" footer and a "with Claude" badge, and the owner wants no Claude attribution anywhere. The verify report was left out, because it is only part of `work-queue`. And cloud threads cannot take screenshots or run hooks. The CLI loop on the Mac mini (ADR-008, ADR-009) already builds, verifies and opens pull requests with the owner's own login.

## Decision

The owner decided (2026-10-26) that each side does one half:
- **The Project** analyses, settles the decisions (Q1, Q2, ...), confirms the design, waits for the owner's OK, and ends at an issue labelled `agent:ready` with the `Decisions` and `Design` comments (`.claude/project-instructions.md`). It does not write code or open pull requests.
- **The issue is posted from the Mac mini**, through a Remote Control session that runs `gh` with the owner's login, so it carries no Claude attribution. When the Mac mini cannot be reached, the thread writes the texts to the project files and the owner posts them. `/redo` comments asked through the Project take the same route.
- **The loop** (`work-queue`, `/loop 30m`) builds, tests, reviews, verifies, pushes and opens the pull request with the report link. It never merges; the owner merges on GitHub.
- `.claude/settings.json` turns off the CLI's default commit and pull request attribution, so the unattended loop cannot add it.

Rejected:
- **Cloud thread posts the issue through the Claude GitHub App:** footer and badge cannot be removed.
- **Cloud thread implements and opens the pull request (ADR-010):** attribution, no verify report, no hooks.
- **A 15-minute loop:** the loop shares the Pro usage limit with the owner; a wait after the OK is acceptable.

## Consequences

- This reverses two points of ADR-010: the `agent:ready` queue is kept (it was rejected there), and the loop machinery stays (ADR-010 planned to remove it).
- The flow depends on the Mac mini being on: it runs the loop and posts the issues. Without it, the owner posts the drafted texts and the loop waits.
- The `Decisions` and `Design` comments are posted with the owner's login and without the loop marker, so `work-queue` treats them as the owner's.
- To verify on the first run: Remote Control posting, the hook prompt before `git push` outside loop mode, the push notification, and that the Mac mini has Chromium for Playwright (without it the masking check is `not run` and the report gets no link).
