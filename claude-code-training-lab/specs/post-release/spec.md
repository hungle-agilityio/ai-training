# Spec: post-release

## Summary

Four steps after a release, in this order of priority. (1) `ops/live_check.py`, run on the Mac mini by the release thread right after `ops/release.py`, waits until `/healthz/` reports the released commit in a new `X-Commit` header, signs in as `demo` on https://reviewradar.onrender.com, opens the nine main screens of `ops/regression_screens.json`, checks the security headers of the security-check epic and prints PASS, SLOW or FAIL per screen with its load time. (2) `ops/rollback.py` rolls Render back to the deploy of the previous `v*` tag through Render's API (Auto-Deploy stays on, `deploy` is never moved) and refuses when the database is persistent and migrations were added. (3) `ops/uptime.py`, run by the loop every 5 minutes, pings `/healthz/` and sends a phone message after two failures in a row and once when the site is back; Sentry receives every server error, without personal data, when `SENTRY_DSN` is set on Render. (4) `ops/a11y_check.py` runs axe-core on the main screens in CI in the light and the dark theme and fails on a serious or critical finding; four lines of `app.css` fix the contrast findings found on `main` today.

Visible to users of the app: the colours of the green and amber badges, the sidebar note and the plain links (AC22). Everything else is the release flow and the hosting.

## User story

As the owner, I want every release checked on the live site, a one-press rollback, and a phone message when the site is down or throws errors, so that a bad release is found and undone before a client notices.

As a client user of ReviewRadar, I want text and links that keep enough contrast in the light and the dark theme, so that I can read every badge and link on the main screens.

## Acceptance criteria

**Release commit on `/healthz/` (T1)**

- **AC1.** `reviews/views.py` `healthz`: when the environment variable `RENDER_GIT_COMMIT` (set by Render at run time) is set and not blank, the response has the header `X-Commit` with its value, stripped. When it is missing or blank, the response has no `X-Commit` header. The variable is read on each request (not at import). Status 200, body `ok`, content type `text/plain`, no database query and the `login_required = False` mark stay as on `main`.
- **AC2.** New tests in `reviews/tests/integration/test_healthz_commit.py` (set, blank, missing; zero queries in each case); every test on `main` passes unchanged.

**Live check after a release (T2)**

- **AC3.** `ops/flow.toml` gets an optional table `[live]` with exactly these keys: `url = "https://reviewradar.onrender.com"`, `wait_minutes = 15`, `load_warn_seconds = 3`, `persistent_database = false`. `ops/flow_config.py` reads it into `FlowConfig.live` (a frozen dataclass `LiveConfig`, or `None` when the table is missing); when the table is there, a missing key or a value of the wrong type stops with the key's name, like the other tables. A flow config without `[live]` loads as on `main`.
- **AC4.** `ops/agent.env.example` documents three new variables, empty, each with a one-line comment: `REVIEWRADAR_DEMO_PASSWORD` (the same value as on Render, used by the live check to sign in as `demo`), `RENDER_API_KEY` (a secret, Render Account settings → API keys, used only by `ops/rollback.py`), `RENDER_SERVICE_ID` (`srv-...`, from the service's URL on Render).
- **AC5.** `uv run python ops/live_check.py [--commit <sha>]` reads the variables from `ops/agent.env` or `agent.env` in the state folder, the same way `ops/agent_tick.py` does. Without `--commit` it runs `git fetch origin` and checks the commit of `origin/deploy`. It stops with exit code 2 and one line, before any request, when the flow config has no `[live]` table (`no [live] table in flow.toml`) or `REVIEWRADAR_DEMO_PASSWORD` is empty (`REVIEWRADAR_DEMO_PASSWORD is not set in agent.env`).
- **AC6.** Given `deploy` was moved to commit `5213e39` and Render still serves `d7738b4` (v2026.11.12), when the check starts, then it asks `<url>/healthz/` every 20 seconds (60-second timeout per request) until the answer is 200 with `X-Commit` equal to the full commit, and prints `live: 5213e39 after <m>m<ss>s`. When `wait_minutes` pass first, it prints `FAIL wait: 5213e39 is not live after 15 minutes (live: d7738b4)` (or `(live: none)` without the header or without an answer), then `result: fail`, and exits 1 without opening a page.
- **AC7.** Given the released commit is live, when the check goes on, then it opens a headless Chromium, signs in as `demo` through `/login/` with the password from AC5, and runs every step of `ops/regression_screens.json` in order (`goto`, `actions`, `expect`; `capture` is ignored). Per step it prints one line: `PASS <name> <s>s`, or `SLOW <name> <s>s (over 3s)` when the load time is above `load_warn_seconds`, or `FAIL <name>: <reason>`. The load time is from the start of the `goto` until the page's `load` event, after the step's actions, in seconds with one decimal. A reason is one of `HTTP <status>`, `missing text "<expected text>"`, `<k> console errors`, `<k> failed requests`, `timeout`. A SLOW step counts as passed. A failed sign-in prints `FAIL sign-in: could not sign in as demo`, then `result: fail`, and stops.
- **AC8.** After the screens, the check makes the five live security checks of the security-check epic (its T1), each one line `PASS <name>` or `FAIL <name>: <reason>`: `https-redirect` (a GET of `http://` + the host of `url` + `/dashboard/`, no redirect followed, answers 301 with a `Location` starting with `https://`); `frame-options` (the `/login/` response over https has `X-Frame-Options: DENY`); `hsts` (it has `Strict-Transport-Security: max-age=31536000`, without `includeSubDomains` and without `preload`); `login-required` (a GET of `/dashboard/` without a session, no redirect followed, answers 302 to a `Location` starting with `/login/`); `healthz` (`/healthz/` over https answers 200).
- **AC9.** The last line is `result: pass` (with `, <k> slow` when steps were SLOW) and exit code 0, or `result: fail` and exit code 1 when any line is FAIL. The check prints no page text other than the expected texts named in a FAIL line, takes no screenshot, writes no file, and never prints the password or the value of any variable from `agent.env`.
- **AC10.** New tests in `ops/tests/test_live_check.py`, with no network: the config and variable refusals of AC5; the wait of AC6 with a fake fetcher and a fake clock (live at once, live after two polls, never live, no header); the step lines of AC7 against pytest-django's `live_server` with a two-step spec (one PASS, one FAIL on a missing text) and a fake clock for SLOW; the five security lines of AC8 with a fake fetcher (all pass, each one failing); the result lines and exit codes of AC9; and the `[live]` table of AC3 (present, missing, a missing key). `ops/README.md` gets a section `## Live check` that says what the command does, its variables and its output. Every test on `main` passes unchanged.

**Rollback (T3)**

- **AC11.** `uv run python ops/rollback.py [--dry-run] [--to <tag>]` runs `git fetch origin --tags`. The current release is the newest `v*` tag (in the order `release.py` gives them: date, then `.2`, `.3`) that points at the commit of `origin/deploy`; the target is the given tag, or else the `v*` tag just before the current one. It refuses with exit code 1 and one line when: no `v*` tag points at `origin/deploy` (`origin/deploy is not a release tag`), there is no earlier tag (`no earlier release to roll back to`), the given tag does not exist or is not an ancestor of `origin/deploy` (`<tag> is not an earlier release`), or `RENDER_API_KEY` or `RENDER_SERVICE_ID` is empty (`<name> is not set in agent.env`).
- **AC12.** It finds the Render deploy of the target with `GET https://api.render.com/v1/services/<RENDER_SERVICE_ID>/deploys?limit=100` (header `Authorization: Bearer <RENDER_API_KEY>`): the newest deploy whose commit id equals the target commit and whose status is `live` or `deactivated`. None found: refuse with `no Render deploy of <tag> (<sha7>) found`. A Render answer other than 2xx: refuse with `Render API failed: HTTP <status>`. The key never appears in any output.
- **AC13.** Given `v2026.11.11` (cd565a7) is live and `v2026.11.10` (d29a13b) is the target, and the commits between them added `reviews/migrations/0006_replytemplate.py` and `reviews/migrations/0007_reviewfollowup.py`, when the rollback runs with `persistent_database = false`, then the plan prints `Migrations since v2026.11.10: 2 (the live database is rebuilt from demo data at start; nothing to reverse)` and goes on; with `persistent_database = true`, it refuses with `2 migrations since v2026.11.10 and the database is persistent: write a reversing migration on main and release it`. Migrations are the added or changed `.py` files other than `__init__.py` under any `migrations/` folder of the app folder (`git diff --name-only <target>..origin/deploy`). With none, the line is `Migrations since <tag>: 0`.
- **AC14.** `--dry-run` prints, in this order: `Current: <tag> <sha7>`, `Roll back to: <tag> <sha7> <commit subject>`, `Render deploy: <deploy id>`, the migrations line, `Pull requests undone:` with one line `  #<n> <title>` per pull request merged between the target and `origin/deploy` (the same format as `release.py`), or `  (none)`, and exits 0. Without `--dry-run` it prints the same lines, sends `POST https://api.render.com/v1/services/<RENDER_SERVICE_ID>/rollback` with the body `{"deployId": "<deploy id>"}`, then prints `Rollback started. Check it with: uv run python ops/live_check.py --commit <full target sha>` and exits 0.
- **AC15.** `ops/rollback.py` never runs `git push`, never creates, moves or deletes a branch or a tag, and never changes a Render setting other than the rollback itself (Auto-Deploy stays on). New tests in `ops/tests/test_rollback.py` with a fixture git repository (three tagged releases, one migration file) and a fake Render client, no network: every refusal of AC11 and AC12, both lines of AC13, the dry-run output of AC14, the POST body, and no push. `ops/README.md` gets a section `## Rollback`. Every test on `main` passes unchanged.

**Uptime alert (T4)**

- **AC16.** `uv run python ops/uptime.py` makes one probe: `GET <url>/healthz/` with a 60-second timeout (the free service may be waking up). Up means status 200 and body `ok`. It keeps its state in `<state_dir>/uptime.json` (`failures`, `down_since` as an ISO time or null, `alerted` true or false). Without a `[live]` table it does nothing and exits 0. It always exits 0.
- **AC17.** Given the last probe failed, when this probe fails too (second failure in a row), then it sends once `ReviewRadar site is down since <HH:MM> (Vietnam time): <reason>` with ntfy priority high (`<HH:MM>` is the time of the first failure; `<reason>` is `HTTP <status>`, `timeout after 60s` or `no connection`); further failures send nothing. Given a message was sent, when a probe succeeds, then it sends once `ReviewRadar site is back after <m> minutes` with priority low and resets the state. One failure followed by a success sends nothing. Messages go to ntfy and Slack with the same variables, title and rules as the tick's messages (`ops/README.md`, "Phone messages").
- **AC18.** `ops/start-loop.sh`: each round of the loop runs `uv run python $REL/uptime.py` after the tick, and a failure of it never stops the loop. New tests in `ops/tests/test_uptime.py` (fake fetcher, fake notifier, temporary state folder, no network): first failure silent, second failure sends the down message once, third silent, recovery message once, one failure then success silent, no `[live]` does nothing, and the `start-loop.sh` line. `ops/README.md` adds both messages to the table of "Phone messages" and a short section `## Uptime`. Every test on `main` passes unchanged.

**Error tracking with Sentry (T5)**

- **AC19.** `pyproject.toml` adds the runtime dependency `sentry-sdk[django]>=2.40` and `uv.lock` is updated with `uv lock`; nothing else in either file changes.
- **AC20.** New module `reviewradar/monitoring.py` with `init_error_tracking(env: Mapping[str, str], debug: bool) -> bool`: when `SENTRY_DSN` in `env` is blank or missing it does nothing and returns False; otherwise it calls `sentry_sdk.init` once with `dsn` = the stripped value, the Django integration, `send_default_pii=False`, `include_local_variables=False`, `max_request_body_size="never"`, `traces_sample_rate=0.0`, `environment` = `"development"` when `debug` else `"production"`, `release` = `RENDER_GIT_COMMIT` or None, and a `before_send` that removes `query_string`, `data` and `cookies` from the event's `request`; it returns True. `reviewradar/settings.py` calls it once at the end with `os.environ` and `DEBUG`.
- **AC21.** `../render.yaml` adds the env var `SENTRY_DSN` with `sync: false` (the owner pastes the DSN on Render once). New tests in `reviews/tests/unit/test_error_tracking.py` (blank, missing, set with `sentry_sdk.init` mocked: every argument of AC20, and `before_send` on an event with `query_string`, `data` and `cookies`) and in `reviews/tests/integration/test_render_sentry_env.py` (the env var with `sync: false`). Every test on `main` passes unchanged.

**Accessibility in CI (T6)**

- **AC22.** Given the demo data and the light theme, when a user opens the dashboard, the reviews list and Settings, then the green badges (`.badge-excellent`, `.badge-positive`, `.followup-resolved`) use text colour `#17753f` on `#e0f5ea` (contrast 5.0, was 4.4), the amber badges (`.badge-watch`, and the status badge of "Reply suggestions" in Settings) use `#8a5c00` on `#fff3d1` (5.3, was 4.4), and the sidebar note "Online reputation management for multi-location businesses." shows at full opacity. Given the dark theme, when a user opens the dashboard, a location page, a reply page, Settings, Reports or Topics, then plain links use the brand colour `#7b93ff` instead of the browser blue `#0000ee`. The change is exactly: `--good: #17753f;` and `--warn: #8a5c00;` in the light `:root` of `reviews/static/reviews/app.css`, a new rule `a { color: var(--brand); }` after the `html` rule, and `opacity: .7;` removed from `.sidebar-note`. On `main` with this change, axe-core 4.10.3 finds no violation on the ten screens of AC23 in either theme (run on 2026-11-12 for this spec).
- **AC23.** A new file `ops/vendor/axe.min.js` is axe-core 4.10.3, unchanged, from https://registry.npmjs.org/axe-core/-/axe-core-4.10.3.tgz (`package/axe.min.js`, SHA-256 `880970c081707360e64f34cea25ff91892f5bc95675b0776925b9709dd8a68bb`). New script `ops/a11y_check.py --spec <file> [--scheme light|dark|both]` (default `both`) starts the app the same way as `.claude/skills/check-in-browser/browser_check.py` (it imports that module's functions by path; it does not change it): a throw-away demo database, the demo seed, a one-run password. It checks the SHA-256 of `ops/vendor/axe.min.js` first (a mismatch: exit 2, `axe.min.js does not match axe-core 4.10.3`). For each scheme it runs axe on `/login/` signed out, then signs in as `demo` and runs every step of the spec (`goto`, `actions`), and runs axe after each. A violation with impact `serious` or `critical` fails; `moderate` and `minor` are printed as `NOTE` and pass. Lines: `PASS <name> <scheme>`, `FAIL <name> <scheme>: <rule id> x<count> (<first selector>)`, `NOTE <name> <scheme>: <rule id> x<count>`; last line `result: clean` (exit 0) or `result: <k> failures` (exit 1).
- **AC24.** `../.github/workflows/checks.yml` gets one step directly after `Browser regression of the main screens` (test-harden T4): `Accessibility of the main screens`, `uv run python ops/a11y_check.py --spec ops/regression_screens.json`. Every other step and the triggers stay as they are. `ops/bootstrap.py` removes this step from the `checks.yml` it copies, the same way it removes the browser regression steps of test-harden T4; the `exclude` list of `ops/bootstrap_manifest.toml` gets `"ops/vendor"` and `LOOP_SKIP` in `ops/bootstrap_layout.py` gets `"vendor"`, so a new project gets neither the step nor the file.
- **AC25.** New tests in `ops/tests/test_a11y_check.py`: the SHA-256 check (match, mismatch); the line format from fake axe results (serious, critical, moderate, none); a browser run on a one-step spec against the app gives `result: clean` for the light scheme; the step of AC24 with its exact `run` line directly after the browser regression step; a bootstrap run into a temporary folder (default layout and `--stack python`) gives a `checks.yml` without the step and no `vendor` folder. Every test on `main` passes unchanged.

## Edge cases

- Empty: no `[live]` table: `live_check` and `rollback` stop with one line, `uptime` does nothing; no `SENTRY_DSN`: no error tracking, the app runs as today; no earlier release tag: the rollback refuses; no pull request between two tags: `  (none)`; no migrations: `Migrations since <tag>: 0`; axe finds nothing: `result: clean`.
- Large data: the live check opens nine fixed screens on the live demo data, so its time does not grow with the data; the Render deploy list is read once with `limit=100` (about 100 releases); `uptime.json` holds three values.
- Slow or sleeping site: the free Render service sleeps after 15 minutes without traffic and needs up to about a minute to wake. The live check and the uptime probe use a 60-second timeout; the uptime ping every 5 minutes keeps it awake (about 720 of the 750 free hours a month).
- Permissions: the commands run only on the Mac mini, by the release thread on the owner's request (rollback after the owner's A); the loop and Claude builds never run `live_check.py` or `rollback.py`. `/healthz/` stays public and shows only a commit id.
- Personal data: the live site holds demo data only (rebuilt at every start), and the live check prints no page text; Sentry gets no user, cookie, request body, query string or local variables.

## Decisions

| Question | Chosen | Rejected | Why |
|---|---|---|---|
| Q1 Where and when does the live check run? | `ops/live_check.py` on the Mac mini, run by the release thread right after `release.py`; result on the release card, a rollback card on FAIL | The tick runs it when `deploy` moves and sends ntfy; a GitHub Actions workflow after deploy (demo password as a repository secret) | The owner sees the result where the release was pressed and can roll back in one step; the demo password stays on the Mac mini |
| Q2 How does the check know the new release is live? | `X-Commit` header on `/healthz/` from Render's `RENDER_GIT_COMMIT` | Wait a fixed 10 minutes | Never checks the old release by mistake; one small change in the app |
| Q3 Rollback command | `ops/rollback.py` with Render's API: dry-run on a card, run after A; `deploy` untouched; the owner makes a Render API key once | Render's Rollback button by hand (turns Auto-Deploy off); revert the changes on `main` and release again | One press, no force push, Auto-Deploy stays on |
| Q4 Rollback across a migration | List the migrations; go on while the database is rebuilt at every start; refuse when `[live] persistent_database = true` | Always refuse; ignore migrations | Works today and is safe the day a real database comes |
| Q5 Alert when the site is down | The loop pings `/healthz/` every 5 minutes; ntfy after two failures in a row, once when back | Ping every 30 minutes; UptimeRobot (external account) | Uses the tick's ntfy, no new account; the site no longer sleeps, so demos open fast |
| Q6 Server errors | Sentry free, `SENTRY_DSN` on Render (blank means off), no personal data | Render log only; Django e-mail to ADMINS (needs SMTP) | An alert and a stack trace; the build is never blocked because a blank DSN turns it off |
| Q7 Accessibility and speed | axe-core in CI on the main screens, fails on serious or critical, today's findings fixed in this epic; load time per screen in the live check, warning above 3 s | Report only; Lighthouse scores in CI | axe findings are stable and real; speed only means something on the real network |
