# Decisions during build: T2 (#506)

| Question | Chosen | Rejected | Why | From |
|---|---|---|---|---|
| What does one cache entry hold? | A frozen dataclass `Attempts`: the count, the time of the first counted failure and the end of the lock | Three separate cache keys; a list of failure times | One read and at most one write per attempt, and the window and the lock are read from the same entry | build |
| When does a count start again? | When the first counted failure is 900 seconds old or more, or when a lock has ended: the next failure is counted as 1 | Keeping the 5 failures after the lock ended | The issue says the lock lasts 15 minutes from the 5th failure and the window starts at the first counted failure; an ended lock is always past its window | build |
| Which username does the form count? | The text as submitted (`self.data`), normalised by the service with `strip()` and `casefold()` | Django's cleaned username | The issue names `self.data`; `Demo ` and `demo` then share one count even though Django signs in case-sensitively | build |
| What happens to an error of `super().clean()` that is not `invalid_login`? | It is raised again and neither counted nor treated as a success | Counting every error | The issue counts only `invalid_login` | build |
| Do spellings such as `ｄemo` (full-width letters) share the count of `demo`? | Yes: the service applies Unicode NFKC before `strip()` and `casefold()`, as Django does before it signs in. For plain text the key is unchanged | Only `strip()` and `casefold()`, as AC4 words it | Django signs `ｄemo` in as `demo`, so without it a locked `demo` still signs in with the right password, against AC2, and each spelling gets its own 4 guesses. The narrowest reading that keeps AC2 and AC4 both true; found by the review | build |
| Is the read-then-write of the count made atomic? | No: wrong passwords for one username sent at the same instant can be counted as one | A lock around the cache entry; `cache.incr` on a separate key | The issue asks for one entry per username in the default cache and no new setting; with the one sync gunicorn worker of today requests run one at a time, with threads or more workers several guesses could count as one | build |
| Where is the count kept on the live site? | In the default cache of the one gunicorn process (local memory); a restart clears every lock | A shared cache (a new setting) | The issue allows no setting and no dependency, and the spec accepts that a restart clears the locks; with more than one worker each would count on its own | build |
| How are the test client responses typed in the new page test? | The helper of `test_login_limit_page.py` is annotated with the test client's response type instead of `HttpResponse` | `HttpResponse`, which `mypy --strict` refuses | A type annotation only; no assertion changed | build |
